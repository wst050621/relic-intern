## 3. 一括登録機能の要求定義

### 3.1 目的

映画館のスタッフが、同じ作品を同じシアターで毎日同じ時刻に上映する予定（例：2週間、10:00・13:30・18:30）を、1回の操作で登録できるようにする。

### 3.2 機能要件

| ID | 要件 | 詳細 |
| --- | --- | --- |
| B-01 | 対象作品 | 1作品を選ぶ。「上映終了」の作品は選べない。選ぶと本編の上映時間を表示する |
| B-02 | シアター | 1シアターを選ぶ（休止中は選べない）。「未割り当て」で登録することもできる（重複検査なし） |
| B-03 | 期間 | 開始日と終了日を入力（日付ピッカーと `20260507` 形式の両方）。終了日は開始日以降、最大31日間。過去の日付は不可 |
| B-04 | 開始時刻 | 1〜10件。カンマ区切りで入力し、フォーカスを外すと正規化・並べ替え・重複除去して、チップとして表示。05:00 より前の時刻は「翌00:30」のように深夜上映として表示 |
| B-05 | 予告時間 | 館の既定値を初期値とし、0〜60分で上書きできる（§5.1） |
| B-06 | 初期状態 | 「下書き」（R2 の方針）。「確定として登録する」を明示的に選んだ場合だけ確定にする |
| B-07 | 終了時刻の目安 | 入力中に「10:00 → 12:19 / 13:30 → 15:49」のように表示する（例は本編124分＋予告15分） |
| B-08 | プレビュー | 「登録内容を確認」で、登録予定の全行（日付・開始・終了・シアター・状態）を表示する。登録はまだしない |
| B-09 | 重複の検出 | プレビューの段階で、各行について (a) 既存の上映回との重複、(b) 今回の登録内容どうしの重複（例：124分の作品を 10:00 と 11:00 で登録）を検出し、相手の上映回と原因を表示する |
| B-10 | 件数の表示 | 「登録予定 28件（14日 × 2回）／重複 2件」のように表示する。重複が1件でもあれば登録ボタンを無効にする |
| B-11 | 登録 | 確認ダイアログの後、全件を1つのトランザクションで登録する。1件でも失敗すれば全件を取り消す。プレビューの後に他のスタッフが登録して重複が生じた場合も、DB の排他制約で拒否し、最新の重複一覧を返す |
| B-12 | 登録後 | 「28件の上映回を登録しました」と表示し、開始日の週の週間表示へ移動する。入力は作品とシアターを残してクリアする（L-08） |
| B-13 | 入力変更時の扱い | プレビュー後に入力を変えたら、プレビューを破棄して登録ボタンを無効にする（古いプレビューでの登録を防ぐ） |
| B-14 | 権限 | 所属スタッフ（admin・staff） |

### 3.3 重複がある場合の扱い（方針の提案）

| 案 | 内容 | 推奨 |
| --- | --- | --- |
| A | 重複が1件でもあれば登録できない。スタッフが時刻や期間を直して再プレビューする | **推奨**（旧管理画面と同じ全件一括の方式。意図しない部分登録を防ぐ） |
| B | 重複しない回だけを登録し、重複した回は登録しない | 不採用（登録されなかった回に気づきにくい） |
| C | 重複した回を「未割り当て」として登録する | 将来の候補（データは失われないが、未割り当てが増える） |

### 3.4 入力検証（旧管理画面のルールを再利用）

| 項目 | ルール | エラーメッセージの例 |
| --- | --- | --- |
| 時刻 | `\d{3,4}` または `\d{1,2}:\d{2}`、0〜23時・0〜59分 | 「時刻「2560」は1000または10:00の形式で入力してください。」 |
| 日付 | 8桁の数字（`/` と `-` は除去）、実在する日付 | 「存在しない日付です。」 |
| 期間 | 終了日 ≥ 開始日、31日以内、開始日 ≥ 今日（「今日以降」は Phase 2 で追加） | 「期間は31日以内で指定してください。」 |
| 開始時刻の件数 | 1〜10件（重複を除いた後） | |
| 合計件数 | 100件以下 | 「一度に登録できる上映回は100件までです。」 |
| 予告時間 | 0〜60 の整数 | |
| 作品・シアター | 同じ館に属する。作品は上映終了でない。シアターは休止中でない | |

### 3.5 旧実装から改善する点

| 旧実装 | Phase 2 |
| --- | --- |
| プレビューでは重複を検出せず、登録時に最初の重複で失敗する | プレビューで全件の重複を一覧表示する |
| 重複メッセージは日時だけ | 相手の作品・シアター・時刻・入れ替え時間を表示する |
| 重複判定はアプリの SELECT（同時に登録すると競合しうる） | DB の排他制約で最終判定する |
| 終了時刻に入れ替え時間を含まない | 占有時間 = 予告 + 本編 + 入れ替え |
| 開始時刻は入力した日付の暦どおりに登録される（「11/1 の 00:30」は 11/1 早朝になり、11/1 の最終回として登録できない） | 営業日の区切りで、前日の深夜上映として扱う |

## 4. シアター管理（整理）

| 項目 | 型・制約 | 旧管理画面 | 提案 |
| --- | --- | --- | --- |
| 名前 | 必須、1〜40字、館内で重複不可、前後の空白を除去 | 必須、1〜100字、全体で重複不可 | 採用（館ごとに重複不可） |
| 座席数 | 任意、1〜5000 | あり | **追加**（表示のみ。予約機能はない） |
| 並び順 | 0以上の整数 | — | 既存の設計どおり |
| 状態 | 利用中 / 休止 | `is_active` | **追加**。休止中は新規登録・一括登録・割り当ての選択肢に出さない。既存の上映回はそのまま残す |

| 操作 | 権限 | 動作 |
| --- | --- | --- |
| 追加・名前の変更・座席数・並び順 | admin | 名前を変えると、すべての上映回の表示に反映される（旧実装のように上映回へ名前をコピーしない） |
| 休止・再開 | admin | 上映回は変わらない。今後の上映回が残っている場合は件数を表示する |
| 削除 | admin | **要判断**（下表） |

| 案 | シアター削除の動作 | 評価 |
| --- | --- | --- |
| 現設計（rev.2） | 上映回を未割り当てに戻す（開始済みの回も含む） | 上映回は残るが、**上映済みの回のシアター情報（履歴）が失われる** |
| 旧実装 | 上映回があれば削除できない | 履歴は残る。スタッフは上映回を移すか削除してから削除する |
| **提案** | 上映回が1件もないシアターだけ削除できる。上映回があるシアターは「休止」にする（今後の回は、スタッフが別のシアターに割り当て直すか未割り当てにする） | 履歴を保ちつつ、作品の扱い（R4：削除不可・上映終了にする）と考え方がそろう |

ローカル検証の指示には「シアター削除時に上映回が未割り当てになる」という項目があるため、提案を採用する場合はこの検証項目も「上映回があるシアターは削除できない」に変更する。

## 5. 詳細設計への影響（採用した場合）

### 5.1 DB（schema-draft.sql）

| 対象 | 変更 |
| --- | --- |
| `theaters` | `default_trailer_minutes int not null default 0 check (0..60)` を追加。初期値0は、今のMVPの終了時刻（開始＋本編）と変わらないようにするため |
| `screens` | `capacity int null check (1..5000)`、`is_active boolean not null default true` を追加。提案どおりなら外部キーを `ON DELETE NO ACTION` に変更 |
| `showtimes` | `trailer_minutes int not null check (0..60)` を追加（未指定なら館の既定値を入れる）。`ends_at = starts_at + 予告 + 本編`、`occupied = [starts_at, ends_at + 入れ替え)` |
| 休止中のシアター | 割り当て・新規登録時に `is_active = false` のシアターを拒否するトリガー（既存の回の編集では、シアターが変わらない限り許可） |
| 一括登録の関数 | `preview_showtime_batch(theater_id, film_id, screen_id, dates date[], times time[], trailer_minutes)`：行ごとに既存・登録内容どうしの重複を返す（SECURITY INVOKER）。`create_showtime_batch(...)`：同じ入力を検証して1文で登録する（排他制約で最終判定）。どちらも上限（31日・10時刻・100件）を DB でも検査する |

### 5.2 API

| 追加・変更 | 内容 |
| --- | --- |
| `POST /api/admin/showtimes/batch/preview` | 一括登録のプレビュー。`{ rows: [{ businessDate, startTime, startsAt, endsAt, conflicts: [...] }], count, conflictCount }` |
| `POST /api/admin/showtimes/batch` | 一括登録。成功で `{ count, ids }`。重複は 409 `OVERLAP` と最新の重複一覧 |
| `GET /api/admin/showtimes` | `from`・`to`（週間表示）に加え、一覧表示用に `screenId`・`status`・並び順・ページ送りを追加 |
| `GET/POST/PATCH/DELETE /api/admin/screens` | admin 向けの CRUD を今回の範囲に含める（rev.2 では「次の段階」としていた）。削除は上映回があれば 409 `SCREEN_HAS_SHOWTIMES` |
| `PATCH /api/admin/theaters/:id` | `defaultTrailerMinutes` を追加 |

## 6. 実装しない方がよい機能

| 機能 | 理由 |
| --- | --- |
| TMDb の検索・取り込み・再取得、モックの TMDb | 商用利用条件の制約（指示どおり） |
| 管理者トークン認証 | 1つの秘密を全員で共有する方式で、館ごとの分離・権限・失効ができない。Supabase Auth と RLS に置き換える |
| 作品と上映予定の一括削除（`delete_schedules=true`） | 上映履歴を消してしまう。R4（削除不可・上映終了にする）と矛盾する |
| 上映予定へのスクリーン名のコピー（`screen_name` 列） | 名前を変えるたびに全行を更新する必要がある。外部キーで参照すれば不要 |
| ポスター画像のアップロード・URL | 画像の権利確認が済むまで扱わない（README §9）。後で扱う場合も、映画館が権利を持つ画像に限り、Supabase Storage と RLS で管理する |
| 評価・投票数・人気度、キャスト・スタッフ・キーワード | TMDb 由来のデータ。手入力で維持するには負担が大きい |
| おすすめ評価の匿名集計 | 今のアプリには評価を集める機能がない。将来、利用傾向分析として別途設計する |
| `window.confirm` による確認 | 見た目がそろわず、スマートフォンで扱いにくい。モックの確認ダイアログを使う |

将来の候補：作品区分（邦画・海外映画）、公式サイト URL（権利上の問題が小さい）、一括登録の曜日指定・除外日、前週からの複製。
